# Shape Up - Solo Builder Approach

## Core Philosophy
**Shape work before building** - make it concrete enough to have boundaries but abstract enough to leave room for creative problem-solving.

## Key Concepts

### Shaping
The pre-work that happens before diving into implementation:
- **Define the problem**: What are we actually trying to solve? Why does it matter?
- **Set boundaries**: What's in scope? What's explicitly out of scope?
- **Sketch the solution**: Breadboard the flow or use fat marker sketches - just enough to show it's feasible
- **Identify rabbit holes**: What could derail this? What unknowns need de-risking?
- **De-risk**: Make sure the approach is sound before committing to build

### Scopes, Not Tasks
- **Think in scopes**: Integrated slices of functionality that deliver value end-to-end
- Each scope is a vertical slice that touches all necessary layers
- Build scope by scope, integrating as you go
- Not about granular task lists - about meaningful chunks of work

### Uphill/Downhill
Mental model for tracking real progress:
- **Uphill**: Figuring out unknowns, solving problems, exploration - this is the hard part
- **Downhill**: Execution of known solutions, just finishing what's been figured out
- Work naturally goes uphill first (problem-solving) then downhill (implementation)
- "Are we uphill or downhill on this?" is more useful than "what % done?"

### Fixed Time, Variable Scope
Personal discipline about knowing when to stop:
- Decide upfront: is this a 2-hour thing, a 2-day thing, or a 2-week thing?
- When that time is up, ship what's done or cut it
- Don't let scope creep turn a small thing into a big thing
- Better to do less well than to never finish

## Working Together (Claude + USER)

### Problem Framing Phase
Before we code anything:
1. What's the problem we're solving?
2. What's in scope? What's out?
3. What are we explicitly NOT doing?

### Shaping Phase
Still pre-code:
1. Breadboard or sketch the solution
2. Identify rabbit holes and unknowns
3. Talk through the approach
4. Get alignment before implementing

### Building Phase
Now we code:
1. Break into scopes (vertical slices)
2. Build scope by scope
3. Each scope moves from uphill → downhill
4. Integrate continuously

## Language & Mindset
- "Let's shape this first" not "Let's start coding"
- "What scope are we on?" not "What's the task list?"
- "Are we uphill or downhill?" not "What % complete?"
- "What are the rabbit holes?" not "What could go wrong?"
- "Is this a 2-hour or 2-day thing?" not "How long will this take?"
- "Let's breadboard this" not "Let's write specs"

## Key Takeaway
Shape Up is about **doing less better** - spend time upfront understanding the problem and sketching a solution so implementation is smooth, focused, and doesn't chase rabbits down holes.
